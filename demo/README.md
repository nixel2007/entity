# Демо: миграции схемы данных

Мини-приложение «Задачник» в трех версиях. Каждый каталог `demo_vN` — полная версия
одного и того же приложения; различия между каталогами показывают эволюцию схемы
и сопутствующие миграции данных. Хранилище — `КоннекторJSON`, каталог `demo/данные`
(создается при первом запуске, в репозиторий не попадает).

Каждая версия состоит из трех слоев:

* `Задача.os` — модель: класс-сущность с аннотациями;
* `СлойДанных.os` — слой данных: единственное место работы с БД
  (менеджер сущностей, версия схемы, регистрация миграций, CRUD-методы для бизнеса);
* `приложение.os` — бизнес-слой: про БД не знает, вызывает методы слоя данных;
* `МиграцияНаВерсиюN.os` — обработчик миграции данных (появляется с версии 2).

## Появилась миграция — что сделать

1. **Измени класс сущности** (`Задача.os`): добавь или удали колонки.
2. **Нужен перенос данных — напиши обработчик** (`МиграцияНаВерсиюN.os`):

   ```bsl
   Функция ВерсияСхемы() Экспорт
       Возврат "2.0.0";                             // версия, к которой привязана миграция
   КонецФункции

   Процедура ПослеМиграции(МенеджерСущностей, ПланМиграции) Экспорт
       // перенос данных через обычные методы менеджера: Получить / Сохранить
   КонецПроцедуры
   ```

3. **В слое данных подними версию схемы и зарегистрируй обработчик**:

   ```bsl
   Менеджер.УстановитьВерсиюСхемы("2.0.0");
   Менеджер.ДобавитьОбработчикМиграции(Новый МиграцияНаВерсию2);
   ```

   Если сквозное обновление со старых версий больше невозможно (миграция опирается
   на колонки, удаленные из модели) — объяви барьер:

   ```bsl
   Менеджер.ПолучитьМиграторСхемы().УстановитьМинимальнуюВерсиюОбновления("2.0.0");
   ```

Больше ничего не нужно: `Инициализировать()` сам сравнит схему БД с моделью,
применит изменения и выполнит обработчики в порядке возрастания версий.
Сравни `СлойДанных.os` соседних версий — разница между ними и есть эти шаги.

Правило жизненного цикла: **обработчики прошлых версий не удаляются** — они переезжают
в следующие версии приложения, пока исполнимы против текущей модели (см. `demo_v2`:
он несет обработчики 1.2.0 и 1.3.0, поэтому прыжок `1.0.0 → 2.0.0` ничего не теряет).
Удалять старые обработчики можно только после объявления барьерной версии (см. `demo_v3`:
барьер `2.0.0` гарантирует, что обработчики 1.x/2.0 никогда не понадобятся).

| Версия | Версия схемы | Схема задачи | Миграции |
| --- | --- | --- | --- |
| [demo_v1](demo_v1) | `1.0.0` | `Идентификатор`, `Имя`, `Выполнена` | — |
| [demo_v1_3](demo_v1_3) | `1.3.0` | + `Срок` (1.1.0), + `Важная` (1.2.0), + `Заметка` (1.3.0) | кумулятивные: [`МиграцияНаВерсию1_2`](demo_v1_3/МиграцияНаВерсию1_2.os), [`МиграцияНаВерсию1_3`](demo_v1_3/МиграцияНаВерсию1_3.os); для 1.1.0 обработчик не нужен |
| [demo_v2](demo_v2) | `2.0.0` | + `Описание`, колонки 1.x сохраняются | [`МиграцияНаВерсию2`](demo_v2/МиграцияНаВерсию2.os): заполняет `Описание` из `Имя`; обработчики 1.x унаследованы |
| [demo_v3](demo_v3) | `3.0.0` | − `Имя`, + `Приоритет`, колонки 1.x сохраняются | [`МиграцияНаВерсию3`](demo_v3/МиграцияНаВерсию3.os): заполняет `Приоритет`; барьерная версия `2.0.0`, обработчики 1.x/2.0 удалены из кода |

Версия 3 объявляет барьер двумя способами сразу (для демонстрации достаточно любого):
`УстановитьМинимальнуюВерсиюОбновления("2.0.0")` на уровне приложения
и `МинимальнаяВерсияСхемы()` на уровне обработчика. Сквозное обновление `1.0.0 → 3.0.0`
невозможно: миграция `Имя → Описание` неисполнима в версии 3, где колонки `Имя` уже нет
в модели. Кроме того, версия 3 включает `УстановитьУдалениеЛишнихКолонок(Истина)`,
поэтому колонка `Имя` физически удаляется из хранилища.

## Запуск

```sh
oscript demo/запустить.os <v1|v2|v3> [чисто]
```

Параметр `чисто` удаляет каталог данных перед запуском (гринфилд-сценарий).
Каждый запуск добавляет одну задачу и выводит содержимое базы.

## Сценарии

Гринфилд и последовательное обновление (все миграции выполняются по очереди):

```sh
oscript demo/запустить.os v1 чисто   # создание таблицы, версия 1.0.0
oscript demo/запустить.os v2         # + колонка Описание, миграция Имя -> Описание, версия 2.0.0
oscript demo/запустить.os v3         # + Приоритет, - Имя, дозаполнение приоритета, версия 3.0.0
```

Минорные версии и кумулятивные миграции. Слой данных версии 1.3 регистрирует **все**
обработчики минорной линейки; мигратор сам выбирает попадающие в интервал
`(ХранимаяВерсия; ВерсияПриложения]` и выполняет их по возрастанию версий.
Обновление `1.0.0 → 1.3.0` одним прыжком выполнит миграции `1.2.0` и `1.3.0` по порядку,
обновление с `1.2.0` — только `1.3.0`. Правка схемы без переноса данных (колонка `Срок`
в `1.1.0`) обработчика не требует вовсе — колонку добавляет дифф:

```sh
oscript demo/запустить.os v1 чисто   # версия схемы 1.0.0
oscript demo/запустить.os v1_3       # 1.0.0 -> 1.3.0: миграции 1.2.0 и 1.3.0 по порядку
oscript demo/запустить.os v2         # 1.3.0 -> 2.0.0: выполняется только миграция 2.0.0
```

Прыжок через минорные версии ничего не теряет: `demo_v2` унаследовал обработчики
линейки 1.x, поэтому при обновлении `1.0.0 → 2.0.0` напрямую конвейер выполнит
`1.2.0`, `1.3.0` и `2.0.0` по порядку:

```sh
oscript demo/запустить.os v1 чисто   # версия схемы 1.0.0
oscript demo/запустить.os v2         # 1.0.0 -> 2.0.0: миграции 1.2.0, 1.3.0, 2.0.0 по порядку
```

Гринфилд сразу на последней версии (baseline: схема создается целевой,
версионные обработчики не выполняются):

```sh
oscript demo/запустить.os v3 чисто
```

Попытка сквозного обновления через барьерную версию (инициализация прерывается,
БД остается нетронутой; после обновления через v2 путь свободен):

```sh
oscript demo/запустить.os v1 чисто
oscript demo/запустить.os v3         # ОШИБКА: минимальная версия схемы для обновления - 2.0.0
oscript demo/запустить.os v2         # промежуточное обновление
oscript demo/запустить.os v3         # успех
```

Попытка понижения версии:

```sh
oscript demo/запустить.os v2 чисто
oscript demo/запустить.os v1         # ОШИБКА: понижение версии схемы не поддерживается
```

Состояние хранилища можно смотреть между запусками в файлах
`demo/данные/Задачи.json` и `demo/данные/entity_ВерсияСхемы.json`.
